# trivy-repo-scanner

Scan a list of local repositories with pinned Trivy 0.76.1 and retain only severity counts. Verify the release checksum and signature before extracting the executable, then record executable and wrapper hashes in each completed report.

Repeated scans can expose dependency problems and committed credentials. Discarding native streams and scanner-provided text prevents matched values from becoming a second collection of secrets.

## Quick start

Requires Python 3.12 or newer and an independently trusted Cosign 3 executable on PATH. Obtain a supported x86_64 release archive, its checksum manifest and its Sigstore bundle from the official Trivy release. No downloader is included.

```sh
python -m pip install -r requirements-dev.txt
python -m pytest -q
python scanner.py verify --archive trivy_0.76.1_Linux-64bit.tar.gz --checksums trivy_0.76.1_checksums.txt --bundle trivy_0.76.1_Linux-64bit.tar.gz.sigstore.json --out verified-tools
python scanner.py run --repos repositories.json --executable verified-tools/trivy --receipt verified-tools/verified.json --out out
```

`repositories.json` is a JSON array of absolute local paths, such as `["/home/developer/projects/app"]`. On Windows, use the `trivy_0.76.1_Windows-64bit.zip` asset and `trivy.exe`. Keep the output folder outside all scanned trees. Do not commit downloaded tools, scan targets or reports.

To schedule on Linux, use absolute paths in a cron entry, for example:

```cron
0 22 * * 0 cd /home/developer/projects/trivy-repo-scanner && /usr/bin/python3 scanner.py run --repos /home/developer/scan-config/repositories.json --executable /home/developer/scan-config/tools/trivy --receipt /home/developer/scan-config/tools/verified.json --out /home/developer/scan-output
```

On Windows, `register-task.ps1` stages a weekly interactive-user task. Review it with `-WhatIf` and provide absolute values for `-Python`, `-Repos`, `-Executable`, `-Receipt` and `-Out`. Registration is a manual step; it is not performed by the code tests. The interactive task requires the user to be logged in.

## Example output

Generated by `python -B demo.py` with synthetic subprocess responses containing one HIGH secret finding. This demonstrates report processing; it does not execute Trivy or verify a real release.

```text
complete=true repositories=1 exit=20
secret_high=1
```

## How it works

The verifier checks SHA-256 against the manifest and asks Cosign to verify the archive bundle with an exact release workflow identity and GitHub Actions issuer. It extracts only the named executable and writes a receipt. Before each run, the binary hash and reported version must match that receipt.

The scan refreshes the vulnerability database once, then uses offline scans with explicit configuration and an empty ignore file. Built-in secret rules stay enabled, and the built-in Markdown exemption is disabled. Environment variables with the Trivy prefix are removed. Trivy can contact database registries during preparation; telemetry is disabled and this wrapper has no upload step. A lock prevents overlap. Each run replaces stale success with an incomplete status before verification begins.

The report stores repository sequence numbers, counts, release provenance and the SHA-256 of `scanner.py`. Native logs, source paths, matches, snippets and titles are discarded. Exit 0 means complete with no HIGH or CRITICAL findings. Exit 20 means complete with such findings, 29 means a rate limit, and 10 means incomplete. A scanner error stops later repositories.

## Limits

Cosign and the local receipt are trust inputs; someone able to replace the receipt and executable can bypass the local hash check. A wrapper hash records provenance but is not a signature. Database availability and age affect results. No real release verification or live Trivy scan is claimed by the mocked tests. Java database preparation is not covered. Signature infrastructure and remote registries may be unavailable. A stale lock requires operator review.
